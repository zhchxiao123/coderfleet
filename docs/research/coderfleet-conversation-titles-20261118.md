# CoderFleet 会话标题：现状、故障实证与改造建议

研究日期：2026-11-18，America/Los_Angeles。

## 结论

用户本次说的“会话总结”是**左侧最近会话、项目会话列表、顶部标签和聊天页标题的自动命名**。目标是从标题认出正在做的事情；日报、工作复盘、长期记忆和模型压缩不属于本次改造。

现状不只是标题文案不理想：**当前配置下，自动命名确实存在稳定复现的生成失败，失败后又永久保留首句截取名。** 还有触发入口不一致、人工命名竞态和视图不同步。因此建议先恢复可靠命名，再改进主题提炼；只替换 prompt 或更换大模型不足以解决。

本轮完成实际安装代码核对、历史标题只读盘点、原函数隔离重放、真实系统模型合成输入实验以及官方协议调研。没有修改生产命名逻辑、已有会话名称、账号配置或服务进程。

## 1. 现有链路实际做了什么

```text
桌面首次发送
  ├─ 取首条消息前 20 个 JS 字符 + "..."，作为 Conversation.name
  ├─ 创建正常 Task，立即开始项目问答
  └─ 浏览器异步尝试自动命名
       ├─ systemLlmConfigured 尚未为 true：直接结束
       ├─ POST /api/summarize-title，只发送首条消息全文
       ├─ 系统模型：最多 16 字的标题，max_tokens=64
       ├─ 另发 PATCH /api/conversations/{id} 保存 name
       └─ 请求失败、空标题、保存失败：静默结束，没有后续补偿
```

手机首次发送只截取前 28 字加省略号；Telegram `/new` 使用前 32 字；CLI 的 `--new-chain` 使用显式传入名称。手机和 Telegram 未调用桌面自动命名函数。桌面 `_autoTitleConversation` 在代码里只有首次新建普通会话后的一个调用点，后续追问、首轮回复结束、重开旧会话均不补命名。

依据：[桌面自动命名](../../coderfleet/server/static/js/chat.js#L3)、[桌面创建链路](../../coderfleet/server/static/js/chat.js#L1960)、[手机发送](../../coderfleet/server/static/mobile.html#L1748)、[Telegram 新会话](../../coderfleet/server/telegram_bridge.py#L841)、[CLI 创建](../../coderfleet/task_cmds.py#L116)、[HTTP 入口](../../coderfleet/server/main.py#L511)、[模型策略](../../coderfleet/server/summarize_title.py#L15)。

这条链路的两次 HTTP 请求没有统一事务：模型只生成一段字符串，浏览器负责最终保存；服务器没有记录这是不是临时名、生成进行到哪一步，或者是否已经被用户人工修改。

只读盘点时间为本地 2026-11-18 08:50 左右。标题模块、系统模型适配器、桌面 chat.js 与已安装包一致；手机 HTML 在归一化构建版本占位符后也一致。因此下面的分析对应当前实际服务使用的实现。

## 3. 已证实的故障

### 3.1 64 token 不足以让当前模型产出标题

当前系统模型为 OpenAI 兼容协议的 `deepseek-flash`。现有 `summarize_title()` 固定请求 `max_tokens=64`，但该模型响应将推理 token 计入 completion 使用量。

同一策略、同一配置，对三个合成输入进行顺序实验：

| 输入 | 64 token 的实际结果 | 相同输入、相同 prompt，改为 256 token |
| --- | --- | --- |
| 明确要求修复历史滚动加载跳动 | `length`，64 completion / 64 reasoning，正文 0 字 | 完成：“修复历史滚动加载跳动” |
| 先读项目规范，再给出上述明确目标 | `length`，64 completion / 64 reasoning，正文 0 字 | 完成：“修复滚动跳动并优先三轮” |
| 仅 `hi` | `length`，64 completion / 64 reasoning，正文 0 字 | 完成：“Greeting”，但识别价值仍低 |

三次 64 token 请求均失败，三次 256 token 对照请求均正常结束。这是当前组合的直接证据；不是声称 256 对所有模型、所有输入都有保证。

现有适配器现在会把 `finish_reason=length` 作为 `SystemLLMOutputLimitError`，HTTP 入口返回 502，前端则静默放弃。此前适配器不检查截断标记时，同类空正文也会被当作空标题跳过。因此近期增加截断检查只是让失败更明确，不能靠取消检查来“恢复”标题。

官方协议分别说明了推理模式与正文的返回方式、completion 的推理用量以及 `length` 的含义；兼容网关的实际行为以上述响应为准，不能直接假定所有官方扩展都可用。[DeepSeek Thinking Mode](https://api-docs.deepseek.com/guides/thinking_mode/)、[Chat Completions](https://api-docs.deepseek.com/api/create-chat-completion/)

证据：[实验程序](../../.scratch/conversation-summary-research-20261118/title_model_probe.py)、[结束原因与用量记录](../../.scratch/conversation-summary-research-20261118/title-model.json)、[适配器](../../coderfleet/server/system_llm.py#L142)。实验没有保存或展示模型推理内容。

### 3.2 一次失败后没有生命周期

前端只在首次提交时尝试一次。系统配置探测稍慢、浏览器关闭、网络短暂失败、模型返回空白、后续 PATCH 失败，都会留下临时名。没有服务端待生成状态、补偿重试、恢复点或“重新生成标题”的入口。

配置已经正确但探测尚未完成，也会被 `if (!systemLlmConfigured) return` 永久跳过。这与“系统模型未配置”是两种情况，目前没有区分。

依据：[自动命名函数](../../coderfleet/server/static/js/chat.js#L5)、[系统模型探测](../../coderfleet/server/static/js/utils.js#L575)。

### 3.3 迟到的自动结果会覆盖用户手动命名

隔离重放实际 `_autoTitleConversation`：

1. 发起自动命名，模型请求保持等待。
2. 用户把会话改为“用户手动命名”。
3. 自动结果返回“迟到的自动标题”。
4. 原函数无条件 PATCH，人工名称被覆盖。

这不是标题质量问题，而是持久化竞态。现有 PATCH 不携带期望版本，Conversation 也没有人工/自动来源字段。[人工改名](../../coderfleet/server/static/js/chat.js#L728)、[服务端改名](../../coderfleet/server/scheduler.py#L1824)、[Conversation 模型](../../coderfleet/server/models.py#L278)

### 3.4 成功后各处标题不一定立即同步

自动命名更新本地会话数组、缓存和侧栏。`syncConversationTabLabels()` 只更新标签数据，不调用标签 DOM 渲染；聊天页标题也没有就地更新。后续列表刷新或重新打开会话可能让部分视图追上，当前打开视图却会暂时保留旧标题。

依据：[自动命名成功分支](../../coderfleet/server/static/js/chat.js#L21)、[标签同步与渲染分离](../../coderfleet/server/static/js/terminal.js#L441)、[聊天页标题模板](../../coderfleet/server/static/js/chat.js#L1556)。

### 3.5 标题的语义输入不足

模型只见首条用户消息，不见后续真正的任务目标或首轮公开回答。因此 `hi`、`继续`、图片占位词、很长的“先读规范”开场都容易产生无区分度的名称。目标在后续消息出现时，也永远没有第二次机会。

当前“≤16 字”只写在提示词里，HTTP 层实际上简单截取前 40 个字符；没有对多行、解释文字、Markdown 包装、原始 URL、泛化标题或内容不足作明确判断。强制短输出预算也不等于保证短标题。

依据：[标题 prompt](../../coderfleet/server/summarize_title.py#L15)、[HTTP 输出处理](../../coderfleet/server/main.py#L518)。

### 3.6 测试只证明能调用模型，没验证标题功能

既有标题测试只有空输入和单次请求/字符串返回。没有覆盖实际配置的推理预算、失败后补偿、手机入口、人工改名竞态、旧标题保护或所有视图同步。

[现有测试](../../tests/test_system_llm.py#L185)

本轮的原函数重放命中了配置晚到、失败无补偿、人工名称覆盖和标题页未直接更新四种现状。它是**问题复现程序**，退出成功表示观察到了这些现状，并非功能已修复或新策略已通过产品验收。

```sh

```

证据：[程序](../../.scratch/conversation-summary-research-20261118/title_probe.cjs)、[结果](../../.scratch/conversation-summary-research-20261118/title-probe.json)。重放模拟了 HTTP 和视图边界；没有浏览器视觉验收。

## 4. 推荐的产品行为

### 4.1 标题概括事情，尽量保持稳定

标题应回答“这条会话在做什么”，建议以**对象 + 问题/动作**命名。避免把“帮我看看”“先读 CLAUDE.md”“接着做”作为名称主体，也不要把“已完成/运行中”塞进标题；现有状态与时间另有位置。

采用以下顺序：

1. 新建立即显示可读临时名，不等模型，不阻塞首条任务。
2. 首条消息目标足够明确时异步生成；目标不足时等待有意义的后续消息/首轮公开回答。
3. 首轮有效上下文到齐后，允许对临时或明显弱的自动标题补一次精炼。已经可靠的标题无需重复调用。
4. 后续标题默认稳定；“继续/好的/下一步”不触发改名。提供“重新生成标题”以处理主题明显转向，不在每轮对话后不断改名。
5. 人工名称优先，并保持锁定。用户主动重新生成时才改变这层优先级。

已有对话/Task/session 的 ID、归属、上下文和执行模式均保持原链；命名只是元数据维护。无需为它创建新的 coding Task、MCP 检索全库或 Agent harness。

### 4.2 少量高价值上下文，避免每次读取全部历史

建议输入包含：项目的显示名、首个实质目标、最近明确目标、必要的首轮公开结论、当前标题及来源。限定文本预算，并保留长输入的目标所在部分，不能简单只截最前面的规范/日志。

命名不需要思考内容、任意工具结果、完整历史日志、认证目录或项目文件。长会话不因为生成几个字就重新解析百兆日志。公开文本选取可复用现有解析/脱敏能力，读取应有 Task/事件水位，避免把正在写入的半条流事件作为结论。

只有附件占位词而没有可用文字时，等待公开回复形成主题；不能假装系统文本模型已经看过图片。

### 4.3 生成预算与文本长度分开

- 先修复当前 64 token 的实测不兼容。考虑带有限重试的合理预算，例如 256 起步，输出受限时扩大到 1024；最终默认值以场景评测决定。
- 具备经过验证的模型能力时，可以为标题单独选择非思考模式；不能对所有 OpenAI 兼容网关强行传厂商字段，也不全局关闭翻译等其他功能的思考。
- 在标题文字上校验非空、单行、去除包装、适当长度和主题有效性。长度限制按可读字符/词处理，不硬切出半个技术标识。
- 中文可以先按 8–24 字、英文 3–8 词做评测目标；这是建议，不是已经确定的强制产品规格。全名完整保存，窄列表用 CSS 省略、悬停显示全文。
- 保留截断检测；任何半份标题不作为成功结果。

### 4.4 上下文策略的小样本可行性实验

用相同系统模型、1024 token 预算和一个候选命名策略，仅给有界的合成“原始目标 + 最近实质消息 + 公开结论”。结果如下：

| 场景 | 模型实际输出 |
| --- | --- |
| `hi` 开场，后续才提出滚动加载问题 | 修复历史消息向上加载的滚动跳动 |
| 先读规范，实际目标是 OAuth 回调问题 | 定位 OAuth 回调后反复跳登录页的原因 |
| Ink 会话列表/提醒目标，最新消息仅“继续” | 完善 Ink 终端会话列表与完成提醒 |
| 只有寒暄与确认 | 延后命名标记 `__DEFER__` |
| 只有图片占位词，没有图片理解结果 | 延后命名标记 `__DEFER__` |

5 个请求均正常结束、均为单行，顺序执行合计 13.83 秒。延后标记只用于实验协议，不能成为用户看到的标题。这说明**少量上下文和合理策略可行**；5 个合成样本不构成真实历史会话质量评分，也没有验证服务端触发、持久化与 UI。

证据：[候选策略与实验](../../.scratch/conversation-summary-research-20261118/title_candidate_probe.py)、[结果](../../.scratch/conversation-summary-research-20261118/title-candidate-model.json)。

## 5. 推荐的实现边界

### 5.1 服务端统一负责生成和条件保存

浏览器不再负责“生成后第二次 PATCH”。桌面、手机和其他自动创建入口共同调用服务端标题服务，异步维护元数据。人工显式名字、CLI `--new-chain NAME`、固定 Workflow/终端名称应保留原意，不被当作临时名。

现有请求中 `conversation_name` 既可能是人工名，也可能是前端拼出的临时名，单凭字段非空无法区分。新入口应显式表达自动/人工意图，并对旧请求保持兼容。

建议状态在 Conversation 或与其一对一的标题元数据中持久化，最少需要：

| 信息 | 为什么需要 |
| --- | --- |
| 来源：legacy / fallback / auto / manual / system | 区分旧未知来源、临时名、自动名、人工名和固定系统名 |
| 状态：waiting_context / pending / ready / retryable_error | 失败、缺上下文与未配置不再混成“无事发生” |
| 标题 revision 与输入水位/hash | 慢响应不覆盖新版本；同一材料不反复生成 |
| 有界重试信息、脱敏错误码 | 重启后有限补偿，避免无限消耗 |

字段必须同时接通存储、API、生成/人工改名路径和 UI 读取，不添加只写不读的占位字段。

保存规则：发起生成时记录来源、revision 和输入水位；返回后通过**统一同步 RMW、并发锁与版本检查**重新读取当前会话，确认仍存在、没有人工改名且版本未变，再原子保存。不能将 `await` 之前持有的 Conversation 整对象写回。API threadpool 与异步任务共享同一入口，不能只依赖事件循环内“不 await”来覆盖跨线程情况。

恢复只处理待生成且仍符合条件的会话。标题失败不修改业务 Task 状态，不阻塞队列、插话、中断或 SDK resume；失败信息放在标题操作详情内，不把错误文本变成标题。

### 5.2 统一显示

收到标题变更后，同时更新最近会话、项目列表、顶部标签、当前会话页标题、快速跳转和手机列表。使用原 Conversation ID 做身份判断，旧页面的迟到响应不能写到新打开的会话。

人工正在编辑标题时保留输入框和内容；不能通过全量重建聊天区来“刷新标题”，否则会破坏草稿、历史滚动锚点、流式回复和待回答表单。可在现有列表刷新/心跳中携带小型标题 revision，避免为改几个字重取全部日志。

CLI 与 Web 使用同一个服务端生成/重命名入口；显式名称保持人工优先，并补齐标题查看、重新生成和历史补全的命令，而非仅在浏览器实现。

### 5.3 旧标题补全

现有数据没有标题来源。对旧会话默认标记 legacy，不能通过“像前缀”直接推断允许覆盖。建议先提供最近会话的候选预览和选中补全，再按项目分批处理；不在启动或打开会话时为 902 条记录一起发模型请求。

批处理需要记录生成前旧名、候选名、材料水位和 revision，只在名字仍等于用户选择时的版本才应用。生成过程中用户手动修改的会话跳过。原文不足或源记录缺失时保留现有名称，并明确可以补充上下文后重试。

## 6. 与 SDK / 厂商标题能力的关系

平台自动命名仍适合沿用系统级模型。Claude SDK 的原生 session 标题与 CoderFleet 的 `Conversation.name` 是两个存储域；直接改原生 transcript 不会自动解决平台侧栏的标题或上述竞态。最新官方存在原生 rename，但固定 SDK 版本是否具备该接口、是否需要双向同步，属于单独兼容性工作。[专项一手资料](coderfleet-conversation-title-primary-sources-20261118.md)

DeepSeek 最新官方另外提供 `title.enabled` 随回答返回标题的扩展，可用作未来减少额外生成请求的候选。但它是供应商扩展，当前第三方兼容网关未验证，项目问答主要运行于 Claude/Codex 等不同后端，也不能靠开启系统模型的一项参数覆盖所有项目会话。[Conversation Title 官方文档](https://api-docs.deepseek.com/guides/conversation_title/)

因此本批不需要迁移执行 SDK 或换主模型。应先建立稳定的平台标题契约，再允许原生标题或厂商扩展作为候选输入。

## 7. 交付顺序与验收

| 切片 | 用户能得到什么 | 必须通过 |
| --- | --- | --- |
| 1. 可靠自动命名 | 新会话能得到真实主题标题，失败可补偿，人工名安全 | 真实系统模型预算；空/截断/超时；桌面手机与服务端触发；人工改名竞态；重启后有限恢复；所有标题视图同步 |
| 2. 更有辨识度的命名 | 寒暄/继续/规范开场不再永久决定标题 | 首个实质目标、首轮公开答复、附件无文字、失败 Task、后续短确认、长技术标识；不扫全历史 |
| 3. 历史标题补全 | 最近旧会话能分批得到更好名称 | 预览与应用同 revision；legacy 不擅自覆盖；取消/重试幂等；断线不重复批量生成；原始旧名有记录 |

可以在一个开发批次打通切片 1、2，但要按端到端行为验收，不先只加模型字段再等前端以后补。切片 3 是显式批处理操作，不默认改写整个历史。

建议建立至少 30 个匿名/合成标题样本：相近主题多个会话、寒暄开场、后续纠正、同项目不同 PR、代码/日志占多数、英语与中英混排、截图开场、首轮失败、主题转向、人工固定名。对比前缀、只读首条的模型标题、有界上下文标题三组。评价维度是辨识度、事实误导、稳定性、长度和成本/等待时间，而非只检查“返回非空字符串”。

确定性回归必须覆盖模型生成期间人工改名/归档/删除、另一个自动版本先完成、会话切换、服务重启和 CLI/API 同时操作。UI 同时验证桌面与窄屏，确认标题更新不重建正文，不破坏此前已优化的历史加载、草稿和流式控制。
