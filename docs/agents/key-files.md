- `coderfleet/server/telegram_bridge.py` — The /new path opts into server-owned conversation naming; explicit names and existing chains retain their current ownership. Telegram long-poll bridge: command routing, topic-per-project registration, broadcast, ASR. All state mutations (offset, per-chat sections, topic registry) must go through `_update_state`/`_set_chat_entry` — a synchronous read-modify-write with no `await` inside the mutator, so it's atomic under the event loop; a separate read-then-write reintroduces the race that `_advance_offset` was written to close (long-poll offset writeback must never clobber a `notify_task` mapping persisted while the poll was suspended). `_ensure_topic` concurrent-create resolves by "first registrant in the state file wins" — a thread created after losing the race is dropped, never re-registered. `is_configured()` is true if `token` and EITHER `chat_ids` OR `topic_group_id` is set — do not require both; group membership is its own trust boundary. `poll_timeout` is 25s, not 50s — proxied long-poll tunnels commonly kill idle connections at 30s+, so a 50s window causes a `ReadTimeout` every round; if you touch the poll loop, keep this under ~28s. `_advance_offset` runs unconditionally after each update regardless of handler success — a poison message must not stall the queue. `_hint_topic_permission_once`'s one-time flag is only persisted after the hint send succeeds — a failed send must retry next round, not burn the one-shot. Broadcast excerpts are extracted by the bridge itself, not reused from the Digest's LLM summary — the Digest summary strips code blocks to `[代码略]` and truncates at 600 chars, which is unacceptable for a code-review broadcast; the bridge's own excerpt keeps code, caps at 3000 chars, with the full message still bounded by Telegram's 4096 hard limit.

- `coderfleet/server/mcp_bridge.py` — Issue #69 Slice 2's MCP server: `build_intervention_mcp(scheduler)` returns a `FastMCP("coderfleet", streamable_http_path="/")` with one registered tool, `ask_user_question`, whose wire name to Claude is `mcp__coderfleet__ask_user_question` (must stay in sync with `renderer.js`'s `ChatLogRenderer.INTERVENTION_TOOL_NAME` and `account_type_registry.py`'s `_claude_mcp_bridge_arg`). Deliberately its own module, NOT folded into `main.py`: FastMCP's `Tool.from_function` does `issubclass(param.annotation, Context)` directly on raw `inspect.signature()` output without resolving PEP 563 string annotations first, so registering a tool from any module carrying `from __future__ import annotations` (which `main.py` has, file-wide) throws `TypeError: issubclass() arg 1 must be a class` for *every* parameter, not just `Context`-typed ones — confirmed by actually running it, not assumed from docs. `streamable_http_path="/"` is required alongside `main.py` mounting this app at `/mcp` — FastMCP's own default path is *also* `/mcp`, so leaving both un-overridden makes the real reachable path `/mcp/mcp`, silently 404ing (also empirically caught, not assumed). The tool takes `ctx` via `mcp_server.get_context()` inside the function body rather than a `ctx: Context` parameter — same PEP-563 issue as above would otherwise misfire on this one parameter even in a future-import-free file if it were typed directly, since `get_context()` sidesteps the auto-detection path entirely; it's also how the code reads the incoming `X-CoderFleet-Task-Id` header via `ctx.request_context.request.headers`. Tool input is typed `list[InterventionQuestion]` (from `models.py`), not a bare `list[dict]` — FastMCP derives the tool's JSON schema Claude actually sees from this type, so using the real Pydantic model (not an untyped dict) is what makes the schema match CC's native `AskUserQuestion` shape (question/header/multiSelect/options) closely enough for the model to construct correct calls; a `/matt-code-review` Spec pass is what caught the original `list[dict]` version as only a partial match. Authenticating *which task* is calling is deliberately just the task id in a header, not a secret — see the tool's own docstring for the accepted trust-boundary trade-off (any container reaching the bridge could in principle spoof another task's id and create a bogus `PendingIntervention` on it; this does not touch the real secret, `PendingIntervention.token`, which still gates the human-answer side from Slice 1) and why closing it fully isn't worth a second token layer given this project's actual threat model (one operator's own accounts, not an external attacker). Verified end-to-end with a *real* `mcp` client (`ClientSession`/`streamablehttp_client`) over `httpx.ASGITransport` in `tests/test_mcp_bridge.py` — no real Docker/network needed, since ASGI-in-process is enough to drive the genuine wire protocol; this is real, checked-in coverage of exactly the layer issue #69's PRD originally called "deliberately outside the test seam" (that assumption predates Slice 2 actually being built — it turned out to be testable). `pyproject.toml` pins `mcp==1.12.4` and `sse-starlette<2.2.0` specifically, not the latest available — newer `mcp` (1.15+) requires `pydantic>=2.11`, and newer `sse-starlette` (2.2.1+) requires `starlette>=0.41.3`, both incompatible with this project's pinned `fastapi==0.115.0`/`pydantic==2.9.2`/`uvicorn==0.30.6`; verify any future `mcp` bump against these three pins via `uv lock --dry-run` before touching the version, the same way this one was checked in. The tool passes `tool_call_id=` through to `scheduler.wait_for_intervention_answer` by reading `ctx.request_context.meta.model_extra.get("claudecode/toolUseId")` — this is Claude Code's own tool_use id, sent via the MCP request's `_meta` field, and it's load-bearing: without it, a fresh random id gets minted instead and the Web UI card (keyed by that same CC tool_use id) can never match the `pending_intervention` it fetches when the user clicks submit — this was a real, 100%-reproducible bug found against a live deployment, not a timing edge case. `meta` can be `None` (client sent no `_meta` at all) and the key can be absent even when `meta` is present (older/other MCP clients) — both fall back to a random id via `wait_for_intervention_answer`'s own default, degrading to "works, but the Web UI card can't correlate precisely" rather than failing. Hermes installs into an isolated venv (`/opt/hermes-venv`) rather than system pip because apt-managed `PyJWT` has no RECORD file and can't be uninstalled by pip if they collide. RTK's installer verifies a SHA-256 checksum before extracting — a supply-chain check; don't swap for an unverified curl-pipe. `USER byclaw` must stay the very last line, after every root-requiring install (apt, playwright system deps) — moving it earlier breaks any subsequent root-only `RUN`. `npm install -g npm@<pinned>` must stay pinned to a specific version below npm/cli's `optionalDependencies`-skipping regression window (`>=11.5.0`, npm/cli #8464/#8628) — floating it back to `npm@latest` silently breaks any npm-installed CLI whose native binary ships as an optional dependency (bit `claude` this way: exits 0, binary just isn't there). Any edit to an *earlier* layer (e.g. the Node.js version line) invalidates Docker's build cache for every layer after it, including this one — an otherwise-unrelated Node bump can resurface this class of bug purely by forcing a fresh `npm@latest`-equivalent resolution; re-verify all npm-installed CLIs (`claude`/`codex`/`opencode`) after touching anything above this line. The pinned SDK is installed into `/opt/coderfleet-claude-sdk-venv` with its bundled CLI via the packaged installer; the main service MCP dependencies and existing non-root user remain separate.
