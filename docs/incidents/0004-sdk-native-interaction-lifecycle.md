# SDK 原生交互在状态同步、导航和重试中的边界错误

## 影响与原因

- 桌面跟随 SSE 日志时关闭了任务心跳；日志流不更新控制就绪字段，发送按钮一直显示“连接中”。心跳先修改缓存状态后，全量刷新又丢失了 pending→running 的变化依据。
- 全量列表失败被当成空列表，可能抹掉已经确认的运行 Task，使补充消息误走新 Task。延迟启动刷新未绑定原 Conversation，导航后会重建另一会话的编辑器。
- 桌面动作查找允许旧 currentChatTaskId 直接兜底，移动端新会话没有刷新旧按钮回调；导航期间可能对旧 Task 请求中断。
- 同会话重绘清空草稿附件，可能把原本带附件的排队请求变成纯文字插话。
- 排队/定时动作优先于未确认回执检查，Task 结束后可能重新提交已送达的文字。
- local/临时路径把控制事件解析复用 session 扫描缓冲；捕获 session 后该缓冲不再更新，导致事件分片丢失或关闭的问题被旧事件重新创建。
- 原生回答仅校验当前 pending 状态，忽略已有持久回执。HTTP 响应丢失后重试报 404；固定答案 ID 被明确拒绝后也不能纠正。
- 原生问题有选项时没有自定义回答；关闭只禁用了提交行中的控件，遗漏行外输入，迟到的网络失败还能覆盖“已回答”。

## 修复

心跳在日志跟随期间继续，原地同步按钮；启动刷新绑定 Conversation，失败保留缓存。页面派发前重新验证 Task 归属，新移动会话刷新动作；同会话刷新保留附件并恢复预览，仅跨会话导航清理。未知回执先于排队和定时。SDK 控制事件采用独立完整行缓冲。原生答案先恢复不可变投递，只有明确拒绝且问题仍有效才允许新尝试，API 提前校验答案类型。问题增加 Other 输入，关闭覆盖全部输入，权威流状态优先于迟到响应。

## 验证与防止再发

每项故障均先在真实页面调用方或 Scheduler.submit/API→mailbox 边界复现红灯，再修复为绿灯。用例位于 tests/frontend/claude-sdk-composer.test.cjs、claude-sdk-renderer.test.cjs 和 tests/test_claude_sdk_interactive_tasks.py。前端必须加载 app.js 的真实计时器入口，并包含异步导航和失败网络，不能只验证已就绪状态；后台必须把一条事件拆成多次 read，并确认关闭事件后不会重放。

验证证据与环境限制见 docs/research/claude-sdk-native-correctness-audit-20261110.md。

## 验证环境发现

本机 Docker 查询持续超时，暴露了保留临时容器替换路径绕过 Runtime、在事件循环内直接同步 docker rm 的问题。该路径改为 await runtime.remove，FakeRuntime 增加清理调用断言。另修正了旧模板目标解析测试：它已有即时完成替身，却仍启动真实 CLI watcher，导致 asyncio.run 结束时偶发无法取消；测试现在替换执行入口，保留原目标解析断言。真实容器和本机真实进程验收的环境失败单独列入审查记录，不能据此宣称全部通过。
