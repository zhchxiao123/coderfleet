# 平台助手读取预算耗尽导致没有回复

## 现象与证据

用户能发送“今天做了哪些事情”，但没有收到回答。只读检查本机原失败运行 `c738e921180b49cd45efa9672e6298b9`（Task `20261112225752-3326`）：执行约 94 秒后失败，最终回答为空。当天快照有 85 个 Task、538 条公开活动，文件 513152 字节。工具已读取 385/538 条，原生结果为 `error_max_turns` / `terminal_reason=max_turns`，配置轮次为 24，费用约 $0.8822。

API 能及时返回失败状态；本次证据没有指向代理断开或任务没有启动。分页 offset 连续前进，没有循环读取同一页。

## 原因

1. **执行策略没有适配实际数据量。** 工具每页最多 20 条且按 16 KB 截断，模型每轮串行读取一页。manifest 和 24 次读取已耗尽预算，还未覆盖全部资料，也没有剩余轮次生成结构化答案。
2. **读取阶段没有为回答预留轮次。** 只有 SDK 的硬上限，没有在达到上限前要求停止检索并明确给出部分回答。
3. **故障反馈丢失。** 失败 Task 返回通用错误，没有保留原生限制原因和读取覆盖率；页面也没有实时读取进度，让用户难以区分正在读取与已经失败。
4. **验收规模不足。** 先前真实模型验收仅有 2 个模拟 Task、4 条活动，证明了隔离、调用和追问链路，无法覆盖实际 85 个 Task 的预算行为。此前通过测试不能代表这一规模可用。

## 修复

- 分页使用完整公开正文的紧凑视图，省略重复宿主来源字段；完整来源仍在冻结快照和来源详情中。单页继续按实际 UTF-8 字节限制在 16 KB 内，最多 100 条。
- manifest 预先给出互不重叠的分页计划，每轮最多 4 个独立读取调用；过滤查询仍按项目/主题缩小范围。全面问答和日报不允许静默采样。
- 按唯一根助手消息 ID 观察读取轮次，为答案预留最后 3 轮。工具返回 `finish_now` 后停止继续提供新资料，要求依据已读内容回答并说明缺口。触及读取预算的问答也标记为部分完成，不伪称完整覆盖。
- 读取工具发布带 Task 身份和快照指纹的进度，原子写入私有工作目录；进度写入失败不会导致正常读取失败。API 校验身份、指纹、整数计数和文件大小，页面显示读取数量和整理阶段。
- 原生轮次/费用限制明确返回失败原因、已读数量和缩小范围的建议。忽略后续合成错误对原生原因的覆盖。不自动重放模型调用，不改写历史失败为成功。

## 验证

原失败运行的只读 HTTP 回归首先稳定复现“error、空答案”，作为红灯。原始数据保持不变，不自动再次发送给模型。

新增回归覆盖：完整分页正文、互不重叠并行计划、根消息 ID 去重、子代理消息排除、预算预留、查询部分完成、原生错误与合成错误优先级、读取回执归属、损坏进度文件、实时进度、失败提示及刷新不重放。

真实模型使用两个新隔离容器，均沿用已授权账号，通过既有 relay 和代理；挂载账号凭据只读，不挂载业务项目或 Docker socket。输入全部由测试脚本新生成，包含 85 个模拟 Task、538 条活动，快照 470633 字节，不包含生产问答。

| 场景 | 配置 | 结果 |
| --- | --- | --- |
| “今天做了哪些事情”全面问答 | 24 轮 / $2 | 538/538 条全部读取，约 45 秒生成 1109 字回答，实际费用约 $0.7683 |
| 同一模拟数据的低预算问答 | 6 轮 / $1 | 读取 132/538 条后保留答案轮次，返回 917 字部分回答，API 明确标记 partial 并提示覆盖缺口 |

第一场景在第 8 个独立根助手消息完成读取；SDK 原生结果的 `num_turns` 为 29。两个计数口径不同，不把工具调用次数当作读取器的轮次观测。两个验收前后既有业务容器的 ID、PID、启动时间一致。

模拟验收证明该规模的执行路径及预算退化行为；不等价于重新总结了用户的真实生产日志。更大输入仍受用户配置的费用、轮次和工具大小上限约束，可能返回部分回答或明确失败。

最终回归：987 项测试全部通过（6 条现有测试警告），包含真实 SDK 协议、隔离 Docker 和 Chromium 页面验收；3 个平台模块严格 mypy 通过，4 项仓库 guard 通过。直接以新读取逻辑检查原生产失败记录，仍保留 error，准确返回 `max_turns` 与 385/538 覆盖率，没有重放模型。
